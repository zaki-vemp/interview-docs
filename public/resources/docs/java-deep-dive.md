# Java Deep Dive: JVM, Memory Model, Concurrency & Modern Java

[Java & Spring Boot](/docs/java) covers the core interview set: OOP, collections, `HashMap`, GC basics, virtual threads, Spring. This doc is the **next layer down**, for rounds that go deep on Java, or where the interviewer knows the Jitsi stack is built from JVM services (Jicofo, the Videobridge and Jibri are Java/Kotlin):

- **JVM internals:** class loading, bytecode and `invokedynamic`, JIT tiers, escape analysis.
- **Memory and GC mechanics:** containers and OOMKills, production diagnosis.
- **The Java Memory Model:** happens-before, safe publication, monitor internals.
- **`java.util.concurrent`:** CAS, thread pools, CompletableFuture, virtual-thread pinning, structured concurrency.
- **Language depth:** generics, sealed types and pattern matching, streams internals, exceptions, reflection and proxies, serialisation, JDK 22–25.

> Java isn't runnable in the browser playground. Two JVM behaviours that are easy to get wrong, **`ThreadPoolExecutor`'s submission policy** and **lazy, per-element stream evaluation**, are simulated in **runnable JavaScript with tests**.

## JVM internals

### Explain class loading: phases, delegation, and class identity 🔥

**Phases:**

1. **Loading:** a class loader finds the bytecode (`.class` in a JAR, a module, generated bytes) and creates a `Class` object.
2. **Linking:**
   - **Verification:** bytecode is type-safe, the stack is balanced, there are no illegal jumps.
   - **Preparation:** static fields are allocated with **default** values.
   - **Resolution:** symbolic references become direct references, often **lazily**.
3. **Initialisation:** runs static initialisers and static field assignments (`<clinit>`). It happens **once**, **thread-safely** (the JVM holds an init lock), and **lazily**, on first active use: `new`, a static method call, a non-constant static field access, reflection, or subclass initialisation.

**Class loader hierarchy (Java 9+):**

| Loader | Loads |
|---|---|
| **Bootstrap** (native) | Core modules: `java.base` (`java.lang.String`) |
| **Platform** | Other platform modules (`java.sql`, `java.xml`…) |
| **Application (system)** | Your classpath and module path |
| Custom loaders | App servers, plugin systems, Spring Boot's `LaunchedClassLoader` for nested JARs, hot-reload tools |

**Parent-first delegation:**

- A loader first asks its parent, and only loads the class itself if the parent can't.
- This guarantees that `java.lang.String` always comes from the bootstrap loader, so nobody can replace core classes.

**Class identity = fully qualified name + defining class loader.**

- The **same class loaded by two loaders gives two different types**.
- Hence `ClassCastException: com.x.Foo cannot be cast to com.x.Foo` in app servers, plugin systems and dev-tools restarts.

**Classloader leaks:**

- Redeploying an app in Tomcat, or hot-reloading, should let the old loader be garbage-collected.
- Any reference from outside keeps **every class it loaded** and their static data alive, causing **Metaspace** growth until `OutOfMemoryError: Metaspace`.
- **Typical culprits:**
  - JDBC drivers registered in `DriverManager`.
  - `ThreadLocal`s on pooled threads.
  - Threads started by the app and never stopped.
  - Shutdown hooks.

**Lazy holder singleton.** This uses the JVM's thread-safe class initialisation, with no locks:

```java
public final class RecorderRegistry {
    private RecorderRegistry() {}
    private static final class Holder {                    // initialised only on first getInstance() call
        static final RecorderRegistry INSTANCE = new RecorderRegistry();
    }
    public static RecorderRegistry getInstance() { return Holder.INSTANCE; }
}
// (Or simply an enum singleton: enum RecorderRegistry { INSTANCE; … })
```

### What does Java bytecode look like, and how do lambdas compile (invokedynamic)? 🔥

**The JVM is a stack machine.** Each method has an operand stack and local variable slots, and bytecode pushes and pops values.

```java
static int add(int a, int b) { return a + b; }
// javap -c:
//   iload_0     // push a
//   iload_1     // push b
//   iadd        // pop two, push the sum
//   ireturn
```

**The five invoke instructions:**

| Instruction | Used for |
|---|---|
| `invokestatic` | Static methods |
| `invokespecial` | Constructors (`<init>`), `private` methods, `super.method()`: no virtual dispatch |
| `invokevirtual` | Normal instance methods: **virtual dispatch** through the vtable |
| `invokeinterface` | Interface methods |
| **`invokedynamic`** (Java 7+) | A **bootstrap method** links the call site at runtime. Used for **lambdas**, **string concatenation** (Java 9+, `StringConcatFactory`), records' `equals`/`hashCode`/`toString` (`ObjectMethods`), and pattern-matching `switch` (`SwitchBootstraps`) |

**How a lambda compiles:**

1. The lambda body becomes a private synthetic method (`lambda$main$0`).
2. The creation site becomes an `invokedynamic` whose bootstrap is **`LambdaMetafactory`**. On first execution it spins up a hidden class implementing the functional interface.
3. **Non-capturing lambdas** are typically a single cached instance. **Capturing** lambdas allocate per evaluation, though escape analysis can often remove that.

**Why `invokedynamic` matters:**

- The **linkage strategy can improve without recompiling** your code (string concatenation got faster in later JDKs with no changes to user code).
- Anonymous inner classes produce a `.class` file each. Lambdas don't.

### How does the JIT compiler work? Explain tiers, inlining and escape analysis 🔥

**Tiered compilation** (HotSpot):

| Level | Executor | Purpose |
|---|---|---|
| 0 | Interpreter | Start immediately; collect invocation and branch counts |
| 1–3 | **C1** (client compiler) | Fast compilation; level 3 adds **full profiling** (types seen, branch frequencies) |
| 4 | **C2** (server compiler) | Aggressive optimisation using the profile |

**Key optimisations:**

- **Inlining:** small, hot methods are copied into callers. This is the **gateway optimisation** that enables everything else, and it's why small getters cost nothing. Monomorphic call sites (one receiver type seen) inline; megamorphic interface calls may not.
- **Escape analysis:** if an object **doesn't escape** the method (not stored in a field, not passed out), C2 can:
  - **Scalar-replace** it: fields become locals, with **no heap allocation**.
  - **Elide locks** on it.
  - That's why short-lived `Optional`s, iterators and builders are often free in hot code.
- **Loop optimisations:** unrolling, range-check elimination, vectorisation (SIMD).
- **Speculative optimisation with deoptimisation:** if a "never null" or "always type X" assumption breaks, the frame **deoptimises** back to the interpreter.
- **OSR (on-stack replacement):** a long-running loop is compiled *while it runs* and execution switches into it mid-loop.

**Warm-up and startup:**

- The JIT needs time, so the first requests are slower. That's why benchmarks need warm-up (**JMH**) and Lambda cold starts hurt Java.
- **Startup solutions:**
  - **CDS/AppCDS** class-data sharing.
  - **Project Leyden's AOT cache**: JDK 24 added AOT class loading and linking; JDK 25 added simpler command-line ergonomics and **AOT method profiling**.
  - **GraalVM Native Image**: full AOT to a native binary. Instant startup and a small footprint, but needs reflection configuration, has a closed world, and no JIT peak (PGO helps).
  - **CRaC / AWS Lambda SnapStart**: checkpoint and restore a warmed JVM.

### Describe JVM memory in detail: object headers, Metaspace, direct memory 🔥

| Area | Holds | Errors |
|---|---|---|
| **Heap** | Objects and arrays. Generational: **young** (Eden + 2 survivor spaces) and **old** | `OutOfMemoryError: Java heap space`, `GC overhead limit exceeded` |
| **Metaspace** (native memory; replaced PermGen in Java 8) | Class metadata, method bytecode, constant pools | `OutOfMemoryError: Metaspace` (classloader leaks, runaway proxy or class generation) |
| **Code cache** | JIT-compiled native code | "CodeCache is full. Compiler has been disabled", so performance collapses |
| **Thread stacks** | One per platform thread (`-Xss`, ~1 MB by default on 64-bit Linux) | `StackOverflowError` (deep recursion); `unable to create native thread` (too many threads) |
| **Direct / native memory** | `ByteBuffer.allocateDirect`, Netty buffers, NIO, JNI, the GC's own structures | `OutOfMemoryError: Direct buffer memory`; container OOMKill |

**Object layout (64-bit HotSpot):**

- **Header** = **mark word** (8 bytes: hash, GC age, lock state) + **class pointer** (4 bytes with compressed class pointers).
- Then the fields, padded to 8-byte alignment. So an `Object` with no fields is 16 bytes, and an `Integer` is 16 bytes **for a 4-byte value**. That's why `List<Integer>` costs ~4–5× an `int[]`.
- **Compressed oops:** with heaps under ~32 GB, references are 4 bytes instead of 8. **Crossing 32 GB can reduce effective capacity**; a classic tuning trivia point.
- **Compact object headers** (JDK 25 product feature, opt-in with `-XX:+UseCompactObjectHeaders`) shrink headers to 8 bytes, cutting heap use for object-heavy apps.

### How do modern garbage collectors work under the hood? 🔥

**Foundations:**

- **GC roots:** thread stacks (locals), static fields, JNI references, the system class loader.
- **Reachability:** anything reachable from the roots is live.
- **The generational hypothesis:** most objects die young. Collect the young generation often and cheaply (copying live objects), and the old generation rarely.
- **Tri-colour marking:**
  - White: not yet seen. Grey: seen, children not scanned. Black: done.
  - With **concurrent** marking, the application keeps mutating references, so **barriers** (code the JIT inserts on reference reads or writes) keep the marking correct.
- **Card tables / remembered sets** track old→young references, so a young collection doesn't scan the whole old generation.

| Collector | Design | Pauses | Use when |
|---|---|---|---|
| **Serial** | Single-threaded, stop-the-world | Long, but tiny overhead | Small heaps, single CPU, small containers |
| **Parallel** | Multi-threaded STW, throughput-oriented | Long-ish | Batch jobs where only throughput matters |
| **G1** (default since 9) | Heap split into equal **regions** (1–32 MB). Young collections, then **mixed collections** that also evacuate the old regions with the most garbage. **Pause-time target** (`-XX:MaxGCPauseMillis=200` by default) | Tens to ~200 ms, mostly predictable | **General-purpose default** for services |
| **ZGC** | **Concurrent** marking and **relocation** using **coloured pointers** and **load barriers**. **Generational** since JDK 21 (the only mode since JDK 24) | **Sub-millisecond**, independent of heap size (up to TBs) | Latency-sensitive services, large heaps |
| **Shenandoah** | Concurrent compaction (load-reference barriers). **Generational mode is a product feature in JDK 25** | Low milliseconds | Low latency (Red Hat builds) |
| Epsilon | No-op (never collects) | — | Testing, extremely short-lived jobs |

**G1 details interviewers like:**

- **Humongous objects** (≥ half a region) are allocated directly in contiguous old regions. Lots of big arrays cause fragmentation and premature full GCs.
- **Evacuation failure** ("to-space exhausted") happens when there's no room to copy live objects, leading to a long pause.

**The tuning method:**

1. **Measure first:** GC logs (`-Xlog:gc*:file=gc.log:time,uptime,level,tags`), JFR, GCeasy/GCViewer.
2. Size the heap properly. **Set `-Xms` = `-Xmx`** for servers to avoid resize pauses.
3. Pick the collector by goal: G1 by default, ZGC for latency.
4. **Reduce allocation rate** in code. This is often the biggest win.
5. **Only then** touch flags.

### Why do Java services get OOMKilled in Kubernetes, and how do you size the JVM? 🔥

**The JVM is container-aware** (`UseContainerSupport`, the default since JDK 10 and backported to 8u191). It reads the cgroup **memory and CPU limits**.

**But the default max heap is only 25% of the container memory** (`MaxRAMPercentage=25`). So:

- Either the heap is far too small (wasted memory, frequent GC),
- **or** people set `-Xmx` equal to the container limit, and the process gets **OOMKilled**, because the **heap is only part of the JVM's memory**:

```text
container limit ≥ heap (-Xmx)
                + metaspace + code cache
                + thread stacks (threads × ~1 MB)
                + direct buffers (Netty!) + GC data structures + native libs + JIT
```

**Practical settings:**

```bash
java -XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=70 \
     -XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=256m \
     -XX:+ExitOnOutOfMemoryError -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
     -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m \
     -jar app.jar
```

**Rules:**

- Leave **25–35% of the container memory for non-heap** use.
- **`ExitOnOutOfMemoryError`**: after an OOM, the JVM state is unreliable, so crash and let Kubernetes restart it, rather than limping along.
- **CPU limits** affect JVM ergonomics. With `limits.cpu: 1`, the JVM may pick **Serial GC** and size thread pools for one CPU. Set `-XX:ActiveProcessorCount`, or give at least 2 CPUs.
- Track **RSS** (container memory) as well as heap usage. Native memory leaks show up only in RSS. **Native Memory Tracking** (`-XX:NativeMemoryTracking=summary`, then `jcmd <pid> VM.native_memory summary`) breaks it down.

### How do you diagnose a production JVM: high CPU, memory leaks, hangs? 🔥

| Symptom | Tools and steps |
|---|---|
| **High CPU** | 1. `top -H -p <pid>` finds the hot **thread id**. 2. Convert it to hex (`printf '%x' 12345`). 3. Take a thread dump (`jcmd <pid> Thread.print` or `jstack <pid>`) and find `nid=0x3039`. Or use **async-profiler** / **JFR** for a CPU flame graph. Common causes: busy loops, regex backtracking, GC thrash (check GC logs first!), serialisation |
| **Memory leak** | Is heap usage after full GCs rising over time? Take a **heap dump** (`jcmd <pid> GC.heap_dump /tmp/heap.hprof`) and open it in **Eclipse MAT**: **Dominator Tree** and **Leak Suspects**, following the path to the GC roots. Classic causes: static maps and caches, listeners, `ThreadLocal`s on pool threads, unbounded queues |
| **Hang / slow requests** | Take **several thread dumps** ~5 s apart. Look for many threads `BLOCKED` on the same monitor (lock contention), threads `WAITING` on a pool or connection (pool exhaustion), and **deadlocks** (`jstack` prints "Found one Java-level deadlock") |
| **Latency spikes** | GC logs: long pauses? JFR events: safepoints, monitor contention, socket reads. **async-profiler wall-clock mode** shows where threads wait, not just where they burn CPU |
| **Continuous** | **JFR** is always on in production at ~1% overhead (`-XX:StartFlightRecording`), analysed in **JDK Mission Control**. Pyroscope or Datadog do continuous profiling |

**Thread states in dumps:**

- `RUNNABLE` (on CPU, or in native I/O).
- `BLOCKED` (waiting to enter a `synchronized` monitor).
- `WAITING` / `TIMED_WAITING` (`park`, `wait`, `sleep`, waiting on a queue).

Virtual threads appear in dumps produced with `jcmd <pid> Thread.dump_to_file -format=json`.

## The Java Memory Model & concurrency

### Explain the Java Memory Model: happens-before and safe publication 🔥

**Why a memory model exists:**

- CPUs and compilers **reorder** instructions and keep values in **caches and registers**.
- Without rules, thread B may see thread A's writes **late, out of order, or never**.
- The **JMM** defines when a write by one thread is **guaranteed visible** to a read in another: when the write **happens-before** the read.

**Happens-before rules (the ones to know):**

| Rule | Meaning |
|---|---|
| **Program order** | Within one thread, each action happens-before the later ones |
| **Monitor lock** | **Unlocking** a monitor happens-before every subsequent **lock** of the same monitor |
| **Volatile** | A **write** to a volatile field happens-before every subsequent **read** of that field |
| **Thread start / join** | `t.start()` happens-before anything in `t`; everything in `t` happens-before another thread's successful return from `t.join()` |
| **Final fields** | After a constructor finishes, other threads see correctly-initialised `final` fields, **if `this` didn't escape during construction** |
| **Transitivity** | If A hb B and B hb C, then A hb C |
| `java.util.concurrent` | Putting into a concurrent collection, `Future.get()`, `CountDownLatch.countDown()`→`await()`, etc. all establish happens-before |

**Safe publication idioms** (making an object visible to other threads, fully constructed):

1. Initialise it from a **static initialiser** (class-init locking).
2. Store it into a **`volatile`** field or an `AtomicReference`.
3. Store it into a **`final`** field of a properly constructed object.
4. Store it into a field guarded by a **lock**.
5. Put it into a **concurrent collection** (`ConcurrentHashMap`, `BlockingQueue`).

**Double-checked locking needs `volatile`:**

```java
public final class Config {
    private static volatile Config instance;               // without volatile: broken
    public static Config get() {
        Config local = instance;                            // one volatile read on the fast path
        if (local == null) {
            synchronized (Config.class) {
                local = instance;
                if (local == null) instance = local = new Config();
            }
        }
        return local;
    }
}
```

**Why it breaks without `volatile`:**

- `instance = new Config()` can be **reordered**: the reference is published *before* the constructor's writes are visible.
- Another thread then sees a **non-null but half-initialised** object.
- `volatile` forbids that reordering and creates the happens-before edge.
- **In practice, prefer the holder idiom or an enum.**

### How does `synchronized` work internally, and what are `wait`/`notify` pitfalls? 🔥

**Monitors:**

- Every object can act as a **monitor**. `synchronized` compiles to `monitorenter`/`monitorexit` (or a method flag).
- **Lock states** live in the object's mark word:
  - **Uncontended:** a cheap CAS-based *thin* (lightweight) lock.
  - **Contention:** the lock **inflates** to a heavyweight monitor, with an OS-level wait queue.
  - **Biased locking** was deprecated in JDK 15 and removed in JDK 18, because modern hardware made it a net loss.
- **Reentrant:** the same thread can re-acquire a monitor it holds (a counter).
- **Memory effects:** entering and exiting give the visibility guarantees above. `synchronized` is about **visibility and atomicity together**.

**Virtual threads:**

- **Before JDK 24**, blocking inside `synchronized` **pinned** a virtual thread to its carrier, a scalability trap.
- **JDK 24 (JEP 491)** lets virtual threads acquire, hold and release monitors without pinning. Pinning remains mainly for **native frames** (JNI) and a few edge cases.

**`wait`/`notify` rules:**

- Call them **only while holding the monitor**, otherwise you get `IllegalMonitorStateException`.
- **Always wait in a `while` loop**, never an `if`:
  - **Spurious wakeups** are allowed.
  - Another thread may have consumed the condition between the notify and your wake-up.
- **Prefer `notifyAll`.** `notify` wakes an arbitrary thread, which may not be the one that can proceed (lost wakeups).
- **In new code, prefer `java.util.concurrent`:** `BlockingQueue`, `Condition`, `CountDownLatch`.

```java
// Correct guarded wait
synchronized (lock) {
    while (queue.isEmpty()) {          // re-check after every wakeup
        lock.wait();
    }
    return queue.poll();
}
```

### `ReentrantLock`, `ReadWriteLock`, `StampedLock`: when are they better than `synchronized`?

| Lock | Adds over `synchronized` | Use when |
|---|---|---|
| **`ReentrantLock`** | `tryLock()` / `tryLock(timeout)` (avoids deadlocks), `lockInterruptibly()`, a **fairness** option, multiple **`Condition`s** per lock | You need timeouts, interruptibility, or separate wait conditions (bounded buffer: `notFull`, `notEmpty`) |
| **`ReentrantReadWriteLock`** | Many concurrent readers **or** one writer | Read-mostly data with non-trivial reads (config, routing tables). It has overhead, and writers can starve without fairness |
| **`StampedLock`** | **Optimistic reads**: read without locking, then `validate(stamp)`, falling back to a read lock if a write happened | Very read-heavy, short reads (coordinates, counters). **Not reentrant**, no Conditions, easy to misuse |

```java
private final ReentrantLock lock = new ReentrantLock();
public boolean transfer(Account a, Account b, long amount) throws InterruptedException {
    // Consistent lock ordering by id prevents deadlock; tryLock with a timeout prevents hanging forever
    Account first = a.id() < b.id() ? a : b, second = first == a ? b : a;
    if (!first.lock().tryLock(100, TimeUnit.MILLISECONDS)) return false;
    try {
        if (!second.lock().tryLock(100, TimeUnit.MILLISECONDS)) return false;
        try { a.debit(amount); b.credit(amount); return true; }
        finally { second.lock().unlock(); }
    } finally { first.lock().unlock(); }                // ALWAYS unlock in finally
}
```

**Rule:** start with `synchronized` (simpler; cannot forget to unlock). Reach for explicit locks when you need their features.

### How do atomics and CAS work? Explain the ABA problem and `LongAdder` 🔥

**Compare-and-swap (CAS)** is a CPU instruction (`cmpxchg`): "**set the value to V only if it is still E**", atomically. Java exposes it through `AtomicInteger`, `AtomicReference`, `VarHandle`, etc.

```java
// Lock-free update loop: read, compute, try to swap; retry if another thread won the race
AtomicReference<Settings> settings = new AtomicReference<>(Settings.defaults());
void enableLobby() {
    Settings prev, next;
    do {
        prev = settings.get();
        next = prev.withLobby(true);              // immutable update
    } while (!settings.compareAndSet(prev, next));
}
// Equivalent helper: settings.updateAndGet(s -> s.withLobby(true));   (fn must be side-effect free — may run several times)
```

**The ABA problem:**

1. Thread 1 reads A and gets delayed.
2. Thread 2 changes A → B → A.
3. Thread 1's CAS(A → C) **succeeds**, even though the structure changed underneath it. In lock-free stacks this corrupts the structure: a node popped and re-pushed.
4. **Fixes:**
   - **Version stamps:** `AtomicStampedReference` compares the reference **and** a counter.
   - Immutable nodes plus GC. In Java, GC prevents memory reuse while references exist, which removes most ABA cases you'd hit in C/C++.

**`LongAdder` vs `AtomicLong`:**

- Under **high contention**, threads spin on the same cache line with `AtomicLong`, and CAS failures waste CPU.
- **`LongAdder`** keeps **striped cells**: each thread increments its own cell, and `sum()` adds them up.
- That makes it **much faster for write-heavy counters** (metrics, request counts), but `sum()` isn't an atomic snapshot.
- `ConcurrentHashMap` uses the same idea for its size counter.

### Which synchronizers do you know, and when would you use each?

| Synchronizer | Semantics | Example |
|---|---|---|
| **`CountDownLatch`** | Wait until a count reaches zero. **One-shot** | Start serving only after 3 caches have warmed; tests waiting for async callbacks |
| **`CyclicBarrier`** | N threads wait for each other at a barrier, then proceed. **Reusable**, with an optional barrier action | Parallel simulation steps, phased batch processing |
| **`Semaphore`** | Permits limit concurrent access | **Limit calls to a downstream service** (with virtual threads, it limits concurrency instead of a pool) |
| **`Phaser`** | A flexible, reusable barrier with a dynamic number of parties | Multi-phase tasks where workers join and leave |
| `Exchanger` | Two threads swap objects | Double-buffering pipelines |
| **`CompletableFuture`** | Async results with composition | Fan-out/fan-in of service calls |

```java
// Limit concurrent calls to the transcoding service to 10, regardless of how many (virtual) threads call it
private final Semaphore transcodeSlots = new Semaphore(10);
public Result transcode(Job job) throws InterruptedException {
    transcodeSlots.acquire();
    try { return client.transcode(job); }
    finally { transcodeSlots.release(); }
}
```

### How does `ThreadPoolExecutor` decide what to do with a new task? 🔥

`new ThreadPoolExecutor(core, max, keepAlive, unit, workQueue, threadFactory, rejectionHandler)` handles each `execute(task)` like this:

1. **Fewer than `corePoolSize` threads?** **Start a new thread**, even if others are idle.
2. **Otherwise, try to put the task in the queue.**
3. **The queue is full?** Start a new thread if there are fewer than `maximumPoolSize`.
4. **Otherwise, reject:**
   - `AbortPolicy` throws `RejectedExecutionException` (the default).
   - `CallerRunsPolicy` runs the task in the caller's thread, which is natural **backpressure**.
   - `DiscardPolicy` / `DiscardOldestPolicy` drop tasks.

**The surprise:** the pool grows past core **only when the queue is full**.

- With an **unbounded queue** (`LinkedBlockingQueue()`, used by `Executors.newFixedThreadPool`), **`maximumPoolSize` is never used**.
- Under overload, the queue **grows without bound** until the service runs out of memory.
- `newCachedThreadPool` has the opposite problem: unbounded **threads**.

```js
// Simulate ThreadPoolExecutor's submission policy
function threadPoolExecutor({ core, max, queueCapacity }) {
  let threads = 0;
  const queue = [];
  const submit = (task) => {
    if (threads < core) { threads++; return 'new core thread'; }
    if (queue.length < queueCapacity) { queue.push(task); return 'queued'; }
    if (threads < max) { threads++; return 'new non-core thread'; }
    return 'rejected';
  };
  return { submit, state: () => ({ threads, queued: queue.length }) };
}

test('core → queue → extra threads → reject', () => {
  const pool = threadPoolExecutor({ core: 2, max: 4, queueCapacity: 2 });
  const outcomes = Array.from({ length: 7 }, (_, i) => pool.submit(`t${i + 1}`));
  expect(outcomes).toEqual([
    'new core thread', 'new core thread', 'queued', 'queued', 'new non-core thread', 'new non-core thread', 'rejected',
  ]);
  expect(pool.state()).toEqual({ threads: 4, queued: 2 });
});
test('with an unbounded queue, max threads is never reached (Executors.newFixedThreadPool)', () => {
  const pool = threadPoolExecutor({ core: 2, max: 50, queueCapacity: Infinity });
  for (let i = 0; i < 10_000; i++) pool.submit(i);
  expect(pool.state()).toEqual({ threads: 2, queued: 9_998 });     // memory grows, latency explodes
});
```

**Production configuration:**

```java
ThreadPoolExecutor exec = new ThreadPoolExecutor(
    16, 32, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),                                    // BOUNDED queue
    Thread.ofPlatform().name("report-", 0).factory(),                 // named threads (readable thread dumps)
    new ThreadPoolExecutor.CallerRunsPolicy());                       // backpressure instead of OOM
```

**Sizing:**

- **CPU-bound:** about `cores` (or cores + 1).
- **I/O-bound:** `cores × (1 + wait time / compute time)`, e.g. 8 × (1 + 90/10) = 80. Or simply use **virtual threads**.
- **Monitor** active count, queue size, rejections and task latency.

**ForkJoinPool:**

- Each worker has a deque and **steals work** from others.
- It's built for divide-and-conquer and recursive tasks, and backs **parallel streams** and the default `CompletableFuture` async executor through the **common pool** (parallelism = cores − 1).
- **Never run blocking I/O in the common pool.** It starves every parallel stream and async task in the JVM. Pass your own executor.

### Explain CompletableFuture composition and error handling in depth 🔥

| Method | Like (JavaScript) | Purpose |
|---|---|---|
| `supplyAsync(supplier, executor)` | `new Promise` / async fn | Start async work, **on an explicit executor** |
| `thenApply(fn)` | `.then(x => y)` | Transform the result (sync function) |
| **`thenCompose(fn)`** | `.then(x => promise)` | Chain **another async call** (flatMap). Using `thenApply` here gives `CompletableFuture<CompletableFuture<T>>` |
| `thenCombine(other, fn)` | `Promise.all([a, b]).then(…)` | Combine two **independent** futures |
| `allOf(f1, f2, …)` | `Promise.all` | Wait for all (returns `Void`; then `join` each) |
| `anyOf(…)` | `Promise.race` | The first to complete |
| `exceptionally(fn)` | `.catch` | Recover from an error with a value |
| `handle((v, ex) -> …)` | `.then(ok, err)` | Handle success or failure, and transform |
| `whenComplete((v, ex) -> …)` | `.finally` (sees the result) | Side effects; doesn't change the result |
| `orTimeout(d)` / `completeOnTimeout(v, d)` | `Promise.race` with a timer | Timeouts (Java 9+) |

```java
ExecutorService io = Executors.newVirtualThreadPerTaskExecutor();

CompletableFuture<MeetingSummary> summary =
    CompletableFuture.supplyAsync(() -> meetingClient.get(id), io)
        .thenCompose(m -> CompletableFuture.supplyAsync(() -> recordingClient.list(m.id()), io)
            .thenCombine(CompletableFuture.supplyAsync(() -> chatClient.stats(m.id()), io),
                         (recs, chat) -> new MeetingSummary(m, recs, chat)))
        .orTimeout(2, TimeUnit.SECONDS)
        .exceptionally(ex -> MeetingSummary.unavailable(id, unwrap(ex)));   // ex is often a CompletionException wrapper
```

**Pitfalls:**

- **Default executor:** the `*Async` methods without an executor use the **common ForkJoinPool**. Blocking calls there starve it.
- **Swallowed exceptions:** a future nobody `join`s or `get`s and that has no `exceptionally` **hides failures**.
- **`CompletionException` / `ExecutionException` wrapping:** unwrap `getCause()`.
- **`join()` inside a pool thread** waiting on a task in the same pool can **deadlock** a bounded pool.
- **Cancellation:** `cancel(true)` doesn't interrupt the running supplier. CompletableFuture isn't wired to the thread.

With **virtual threads**, plain blocking code inside `StructuredTaskScope`, or a virtual-thread executor, often replaces complex CompletableFuture chains.

### Virtual threads in depth: mounting, pinning, and structured concurrency 🔥

**How they work:**

- A **virtual thread** is a `Thread` managed by the JVM.
- It **mounts** on a **carrier** platform thread (from a ForkJoinPool sized to the CPU count).
- When it blocks on I/O, `sleep`, a lock or a queue, the JVM **unmounts** it. Its stack frames are saved as a **continuation** on the heap, and the carrier runs another virtual thread.
- **Blocking becomes cheap**, so **millions** of virtual threads are possible, and simple thread-per-request blocking code scales like async code.

**Rules and pitfalls:**

| Rule | Why |
|---|---|
| **Don't pool virtual threads** | They're cheap. Use `Executors.newVirtualThreadPerTaskExecutor()` or `Thread.ofVirtual().start()` |
| **Limit downstream concurrency with a `Semaphore`** | Pools used to cap DB connections or API calls by accident. Now 100,000 virtual threads can all hit the database at once, so the **connection pool** (HikariCP) becomes the limit and needs sensible timeouts |
| **Pinning** | A virtual thread can't unmount while in **native code** (JNI) or, **before JDK 24**, inside `synchronized`. Diagnose with JFR `jdk.VirtualThreadPinned` events. On JDK 21–23, replace `synchronized` around blocking I/O with `ReentrantLock` |
| **Avoid heavy `ThreadLocal` caches** | A million threads × a cached 1 MB buffer each is a problem. Prefer **Scoped Values** for context |
| **CPU-bound work gains nothing** | Virtual threads help **I/O-bound** concurrency, not computation |

**Spring Boot 3.2+:** `spring.threads.virtual.enabled=true` runs Tomcat request handling and `@Async` on virtual threads.

**Structured concurrency** (`StructuredTaskScope`, a preview API through JDK 25) treats a group of concurrent subtasks as **one unit of work**:

- Subtasks can't outlive the scope.
- If one fails, the others are **cancelled**.
- Thread dumps show the parent-child relationships.

```java
// JDK 25 preview API (--enable-preview); the API shape changed across previews
Response handle(long meetingId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {                     // default: fail if any subtask fails
        Subtask<Meeting> meeting = scope.fork(() -> meetings.get(meetingId));
        Subtask<List<Recording>> recordings = scope.fork(() -> recordingsClient.list(meetingId));
        scope.join();                                                   // waits; on failure cancels the siblings and throws
        return new Response(meeting.get(), recordings.get());
    }
}
```

**Scoped Values** (final in JDK 25) are immutable, bounded-lifetime context such as request id or tenant. They're cheaper and safer than `ThreadLocal`, and they're inherited by structured subtasks:

```java
static final ScopedValue<String> TENANT = ScopedValue.newInstance();
ScopedValue.where(TENANT, "acme").run(() -> service.handle());          // TENANT.get() == "acme" inside, unbound outside
```

### How do the concurrent collections work internally? 🔥

**`ConcurrentHashMap`** (Java 8+):

- An array of bins, with **no segments** any more. That was the Java 7 design.
- Reads are **lock-free** (volatile reads).
- An insert into an **empty bin uses CAS**. A non-empty bin is updated under **`synchronized` on the bin's head node**, so contention is per bin.
- Long collision chains **treeify** into red-black trees (≥ 8 entries, with table size ≥ 64).
- **Resizing is cooperative:** threads that touch a map mid-resize **help transfer** bins.
- **`size()`** uses `LongAdder`-style counter cells: an approximation under concurrency. `mappingCount()` returns a long.
- **Iterators are weakly consistent:** they never throw `ConcurrentModificationException`, and may or may not reflect concurrent updates.
- **Null keys and values aren't allowed**, because `null` would be ambiguous with "absent" in concurrent `get`.

**`computeIfAbsent`, `compute` and `merge` are atomic per key, with caveats:**

- The function runs **while holding the bin lock**. Keep it short and side-effect free.
- **Never update the same map inside the function** ("Recursive update" → `IllegalStateException` since Java 9, or a deadlock in Java 8).

```java
// Atomic counters per key
ConcurrentHashMap<String, LongAdder> joinsByRoom = new ConcurrentHashMap<>();
joinsByRoom.computeIfAbsent(roomId, k -> new LongAdder()).increment();

// ✗ Not atomic: check-then-act race between containsKey and put
if (!map.containsKey(k)) map.put(k, create());
// ✓
map.computeIfAbsent(k, key -> create());
```

| Collection | Design | Use |
|---|---|---|
| `CopyOnWriteArrayList` | Every write copies the array; reads are lock-free snapshots | **Read-mostly** lists (listeners, configuration). Terrible for frequent writes |
| `ConcurrentLinkedQueue` | Lock-free linked queue (Michael-Scott) | Non-blocking producer/consumer |
| `ArrayBlockingQueue` | Bounded, one lock, array-backed | **Bounded work queues** (backpressure) |
| `LinkedBlockingQueue` | Optionally bounded, separate put and take locks | Higher throughput queues. **Unbounded by default**: careful |
| `SynchronousQueue` | Zero capacity: a handoff | `newCachedThreadPool`; direct handoff |
| `PriorityBlockingQueue` / `DelayQueue` | Unbounded heap / items available after a delay | Scheduling, retries with delays |
| `ConcurrentSkipListMap` | Lock-free **sorted** map, O(log n) | Concurrent ordered data, leaderboards, time-indexed events |

### What are the common concurrency bugs, and how do you find them?

| Bug | Example | Fix |
|---|---|---|
| **Race: check-then-act** | `if (!map.containsKey(k)) map.put(k, v)` | Atomic operations (`putIfAbsent`, `computeIfAbsent`), locks |
| **Race: read-modify-write** | `count++` on a shared field (not atomic even if `volatile`) | `AtomicInteger`/`LongAdder`, or a lock |
| **Visibility** | A `boolean running` flag without `volatile`: the loop never sees the update | `volatile`, or atomics |
| **Deadlock** | Two locks acquired in opposite orders | Global lock ordering, `tryLock` with timeouts |
| **Livelock** | Threads keep reacting to each other and make no progress (polite retries) | Randomised backoff |
| **Starvation** | Unfair locks; long tasks hogging a pool; writer starvation in RW locks | Fair locks, separate pools, bounded work |
| **Thread or pool leaks** | `Executors.newFixedThreadPool` per request, never shut down | Shared, managed executors; `try-with-resources` on `ExecutorService` (Java 19+ `AutoCloseable`) |
| **ThreadLocal leaks** | Pooled threads keep request data (and classloaders) | `remove()` in `finally`; Scoped Values |
| **Unsafe publication** | Sharing a non-final, non-volatile mutable object | Safe-publication idioms, immutability |

**Finding them:**

- Thread dumps, plus `jstack` deadlock detection.
- **JFR** lock and monitor events.
- Static analysis: **SpotBugs**, **Error Prone** (`@GuardedBy`).
- Concurrency stress testing: **jcstress**.
- **Code review with the question "what if two threads run this at once?"**.
- **Immutability is the best prevention.**

## Language deep dive

### Generics beyond PECS: erasure consequences, bridge methods, heap pollution 🔥

**What type erasure means in practice:**

```java
// ✗ Not allowed because of erasure
T obj = new T();                          // the type isn't known at runtime → pass a Supplier<T> or Class<T>
if (list instanceof List<String>) {}      // only "List<?>" can be checked
static <T> T[] arr = new T[10];           // generic array creation is forbidden
void save(List<String> a) {}  void save(List<Integer> b) {}   // same erasure → "name clash" compile error

// ✓ Type tokens recover the type
<T> T readJson(String json, Class<T> type) { return mapper.readValue(json, type); }
// For generic types, Jackson's TypeReference captures them via an anonymous subclass:
List<Meeting> list = mapper.readValue(json, new TypeReference<List<Meeting>>() {});
```

**Generics vocabulary:**

- **Reifiable types** are fully available at runtime: primitives, non-generic classes, raw types, `List<?>`. `List<String>` isn't reifiable.
- **Bridge methods:** when a class implements `Comparable<Meeting>`, the compiler generates a synthetic `compareTo(Object)` that casts and delegates to `compareTo(Meeting)`, so overriding works after erasure. You see them in stack traces and reflection.
- **Heap pollution:**
  - A variable of a parameterised type refers to an object of a different parameterisation (`List<String>` actually holding Integers).
  - It's caused by raw types, unchecked casts, and **generic varargs** (`T...` creates a `T[]`, i.e. an `Object[]`).
  - **`@SafeVarargs`** promises the method doesn't misuse its varargs array.
- **Recursive bounds:** `<T extends Comparable<? super T>> T max(Collection<? extends T> c)`.
  - `? super T` lets `max` work with a type whose comparison is inherited: `LocalDate` implements `Comparable<ChronoLocalDate>`.
  - **Self-types / fluent builders:** `abstract class Builder<B extends Builder<B>> { B self(); }`.
- **Wildcard capture:**
  - You can't `list.set(0, list.get(0))` on a `List<?>`.
  - A private generic helper method "captures" the wildcard: `<T> void swapHelper(List<T> l, …)`.

### Model a domain with records, sealed types and pattern matching (Java 21+) 🔥

**Sealed hierarchies plus records** give **algebraic data types**: a closed set of variants, so the compiler can **check exhaustiveness** in `switch`.

```java
public sealed interface MeetingEvent permits ParticipantJoined, ParticipantLeft, RecordingStarted, RecordingFailed {}
public record ParticipantJoined(String meetingId, String userId, Role role) implements MeetingEvent {}
public record ParticipantLeft(String meetingId, String userId, Duration stayed) implements MeetingEvent {}
public record RecordingStarted(String meetingId, String recorderNode) implements MeetingEvent {}
public record RecordingFailed(String meetingId, String reason, int attempt) implements MeetingEvent {}

String describe(MeetingEvent e) {
    return switch (e) {                                                   // exhaustive: no default needed
        case ParticipantJoined(var m, var u, Role role) when role == Role.HOST -> "Host " + u + " opened " + m;
        case ParticipantJoined(var m, var u, var _)                    -> u + " joined " + m;      // record pattern + unnamed var (Java 22)
        case ParticipantLeft(var m, var u, Duration d)                 -> u + " left after " + d.toMinutes() + " min";
        case RecordingStarted(var m, var node)                         -> "Recording on " + node;
        case RecordingFailed(var m, var reason, int attempt) when attempt >= 3 -> "Recording abandoned: " + reason;
        case RecordingFailed f                                          -> "Retrying recording (" + f.attempt() + ")";
    };
}
// Add a new permitted subtype → every non-exhaustive switch becomes a COMPILE error. That's the point.
```

**Records:**

- Final, shallowly immutable data carriers.
- **Canonical, compact constructors** for validation (`record Range(int lo, int hi) { Range { if (lo > hi) throw …; } }`).
- `equals`, `hashCode` and `toString` are generated. Accessors are `name()`, not `getName()`.
- **Records are shallowly immutable:** a `List` component can still be mutated, so copy defensively (`List.copyOf`).
- **Not suitable as JPA entities** (they need mutability and a no-arg constructor), but **perfect for DTOs and projections**.

**Pattern matching features to name:**

- `instanceof` patterns (`if (o instanceof String s)`).
- Type patterns in `switch`.
- **Record patterns** (nested deconstruction).
- **Guards** (`when`).
- **Unnamed variables** `_` (Java 22).
- **Primitive patterns** (preview in JDK 25).

### How do streams work internally? Laziness, short-circuiting and parallel pitfalls 🔥

**How a pipeline executes:**

- A stream is a **lazy pipeline**: source → intermediate operations → **one terminal operation**. Nothing runs until the terminal operation.
- Elements flow **one at a time through the whole chain** ("vertical" processing), not stage by stage.
- So `filter().map().findFirst()` stops as soon as one element passes.

**Operation types:**

| Kind | Examples | Notes |
|---|---|---|
| Stateless intermediate | `filter`, `map`, `flatMap`, `peek` | Per element |
| **Stateful intermediate** | `sorted`, `distinct`, `limit`/`skip` (ordered) | Must see many or all elements: they **buffer** (`sorted()` on an infinite stream never ends) |
| **Short-circuiting** | `limit`, `findFirst`, `anyMatch`, `takeWhile` | Can finish without consuming everything |
| Terminal | `collect`, `reduce`, `forEach`, `count`, `toList()` (Java 16) | Triggers execution; the stream can't be reused |

**Under the hood:**

- The source provides a **`Spliterator`** with characteristics (`SIZED`, `ORDERED`, `DISTINCT`, `SORTED`).
- These let the library skip work. `count()` on a SIZED stream may not run `peek`/`map` at all (Java 9+), so **never rely on side effects in intermediate operations**.

The simulation contrasts Java's per-element pipeline with JavaScript's eager array methods:

```js
// Java-style lazy stream (generators) vs eager JS arrays, logging every operation
function* source(items, log) { for (const x of items) { log.push(`emit ${x}`); yield x; } }
function* filter(it, pred, log) { for (const x of it) { log.push(`filter ${x}`); if (pred(x)) yield x; } }
function* map(it, fn, log) { for (const x of it) { log.push(`map ${x}`); yield fn(x); } }
function findFirst(it) { for (const x of it) return x; return undefined; }

const nums = [1, 2, 3, 4, 5, 6];

const lazyLog = [];
const lazy = findFirst(map(filter(source(nums, lazyLog), (n) => n % 2 === 0, lazyLog), (n) => n * 10, lazyLog));

const eagerLog = [];
const eager = nums.filter((n) => { eagerLog.push(`filter ${n}`); return n % 2 === 0; })
                  .map((n) => { eagerLog.push(`map ${n}`); return n * 10; })[0];

test('Java streams process element by element and short-circuit', () => {
  expect(lazy).toBe(20);
  expect(lazyLog).toEqual(['emit 1', 'filter 1', 'emit 2', 'filter 2', 'map 2']);   // stopped after the first match
});
test('eager array methods process stage by stage over everything', () => {
  expect(eager).toBe(20);
  expect(eagerLog).toHaveLength(6 + 3);   // all 6 filtered, all 3 evens mapped
});
```

**Collectors worth knowing:**

```java
Map<Role, Long> countByRole = participants.stream().collect(groupingBy(Participant::role, counting()));
Map<String, Duration> longestStayPerMeeting = sessions.stream()
    .collect(toMap(Session::meetingId, Session::duration, (a, b) -> a.compareTo(b) >= 0 ? a : b));  // merge fn avoids IllegalStateException on duplicate keys
Map<Boolean, List<Meeting>> splitByRecording = meetings.stream().collect(partitioningBy(Meeting::recorded));
var stats = recordings.stream().collect(teeing(counting(), summingLong(Recording::sizeBytes), Stats::new));  // two collectors, one pass
Map<String, Set<String>> usersPerMeeting = sessions.stream()
    .collect(groupingBy(Session::meetingId, TreeMap::new, mapping(Session::userId, toSet())));
```

**Stream Gatherers** (final in JDK 24) add **custom intermediate operations**: `stream.gather(Gatherers.windowFixed(10))`, `windowSliding`, `fold`, `mapConcurrent(maxConcurrency, fn)`. The last one is great with virtual threads.

**Parallel streams pitfalls:**

- They run in the **common ForkJoinPool**: blocking I/O starves the whole JVM.
- Splitting costs: `LinkedList` and `Stream.iterate` split badly; `ArrayList` and arrays split well.
- **Ordered operations** (`findFirst`, `limit`, `forEachOrdered`) on parallel streams are expensive.
- **Shared mutable state** in lambdas causes races.
- Boxing overhead: use `IntStream`/`LongStream`.
- **Rule:** use them only for CPU-bound work on large, splittable data, **measured with JMH**.

### Unmodifiable vs immutable: how do you build truly immutable objects?

| | Mutation through it | Underlying data can change? |
|---|---|---|
| `Collections.unmodifiableList(list)` | Throws `UnsupportedOperationException` | **Yes**: it's a **view**, and changes to the original list show through |
| `List.copyOf(list)` / `List.of(…)` (Java 9/10) | Throws | **No**: an independent immutable copy. **Nulls aren't allowed** |
| `stream.toList()` (Java 16) | Throws | No (an unmodifiable list; nulls allowed) |
| Guava `ImmutableList` | Throws | No |

**Recipe for an immutable class:**

1. `final` class, or a sealed hierarchy, so subclasses can't add mutability.
2. `private final` fields, no setters.
3. **Defensive copies** of mutable inputs in the constructor and of mutable outputs in getters (`List.copyOf`, `new Date(d.getTime())`).
4. Don't let `this` escape during construction.
5. Prefer immutable field types: `java.time`, records, `List.of`.

**Why it matters:** **thread safety for free** (no synchronisation; safe publication via final fields), safe use as map keys, easy caching and sharing, simpler reasoning. **"Withers"** (`settings.withLobby(true)`) give fluent updates.

### Exceptions in depth: try-with-resources, suppressed exceptions, `finally` traps, interruption 🔥

```java
// try-with-resources: closes in REVERSE order; close() failures are attached as SUPPRESSED exceptions
try (var in = Files.newInputStream(src); var out = Files.newOutputStream(dst)) {
    in.transferTo(out);
} catch (IOException e) {
    for (Throwable s : e.getSuppressed()) log.warn("close failed", s);
    throw new UncheckedIOException("copy failed: " + src, e);      // translate + keep the cause
}

// ✗ return in finally SWALLOWS the exception (and overrides the return value)
int risky() {
    try { throw new IllegalStateException("boom"); }
    finally { return 42; }                                          // the exception is lost silently
}

// ✓ InterruptedException: either propagate it, or restore the interrupt flag
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();                             // let callers and the executor see the interruption
    throw new CancellationException("worker interrupted");
}
```

**Points:**

- **Checked exceptions and lambdas don't mix.** `Function` can't throw `IOException`, so you wrap in `UncheckedIOException` or use a sneaky-throw helper. Many modern APIs (and Kotlin) drop checked exceptions entirely.
- **Exceptions are expensive mainly because of the stack trace capture.**
  - **Don't use them for control flow.**
  - For high-volume expected failures, return result types (an `Optional`, or a sealed `Result`).
  - Or create exceptions with `writableStackTrace = false`.
- **Exception translation at layer boundaries:** `SQLException` → `DataAccessException` (Spring does this). Always keep the **cause**.
- **Never catch `Throwable`/`Error`** (OOM, StackOverflow) except at the very top level for logging.
- **Swallowing `InterruptedException`** breaks cancellation and graceful shutdown: executors can't stop your task.

### How do frameworks use reflection, annotations and proxies? 🔥

**Reflection** (`Class`, `Method`, `Field`, `getDeclaredAnnotations()`):

- Frameworks discover beans, inject fields, map JSON (Jackson) and entities (Hibernate).
- **Costs:** slower than direct calls (largely optimised now), it breaks encapsulation, and **GraalVM native images need reflection metadata**.
- **Annotations** are just metadata, with retention `SOURCE`, `CLASS` or `RUNTIME`. Frameworks read the `RUNTIME` ones reflectively.

**Annotation processing at compile time** (javac plugins) **generates code** instead:

- **Lombok** modifies the AST via internal APIs.
- **MapStruct** generates mappers.
- **Dagger** does DI.
- **Micronaut and Quarkus** do much of their DI at build time.
- The benefits are faster startup and no reflection.

**Dynamic proxies power AOP** (`@Transactional`, `@Cacheable`, `@Async`):

| Proxy type | How | Limits |
|---|---|---|
| **JDK dynamic proxy** (`java.lang.reflect.Proxy`) | Implements **interfaces** at runtime; calls go to an `InvocationHandler` | Only interface methods |
| **CGLIB / ByteBuddy subclass proxy** (Spring's default for classes) | Generates a **subclass** that overrides methods | **Can't proxy `final` classes or methods, or `private` methods** |

**The proxy pitfall everyone hits (Spring):**

- **Self-invocation** (`this.method()` inside the bean) **bypasses the proxy**, so `@Transactional`, `@Cacheable` and `@Async` silently do nothing.
- Fix it by moving the method to another bean, or by injecting the bean's own proxy.

**JPMS (modules):**

- Strong encapsulation means reflection into non-exported packages fails (`InaccessibleObjectException`).
- Fix it with `opens` in `module-info.java` or `--add-opens` (common with older libraries on JDK 17+).

**Method handles and VarHandles** are faster, typed reflection-like access. The JDK itself uses them internally.

### Strings: compact strings, concatenation, and what changed

**How strings work today:**

- **Compact strings** (Java 9): a `String` stores a `byte[]` plus a coder flag. **Latin-1 strings use 1 byte per char** instead of 2, which roughly halves string memory for typical text.
- **Concatenation** (Java 9+): `a + b + c` compiles to `invokedynamic` → `StringConcatFactory`, which is efficient for a single expression.
- **In loops, still use `StringBuilder`.** `s += x` in a loop creates a new string each iteration, which is O(n²).

**Other tools:**

- `String.join`, `Collectors.joining`, `String.format` / `"…".formatted(…)`. Formatting is **slow** in hot paths.
- **Text blocks** (Java 15): multi-line literals with indentation stripping. Great for SQL and JSON in tests.

**Equality and the pool:**

- **The string pool:** literals are interned. `==` compares references, so **always use `equals`**.
- `intern()` is rarely useful today.

**History:** **string templates** (`STR."Hello \{name}"`) were previewed in JDK 21–22 and then **withdrawn in JDK 23**. They're not part of Java.

### What are the dangers of Java serialization, and what do you use instead? 🔥

**Native Java serialization** (`Serializable`, `ObjectInputStream`):

- **Deserialising untrusted data is a remote-code-execution risk.** "Gadget chains" in classpath libraries (Commons Collections, Spring) run code during `readObject`. This was behind major breaches.
- It's also slow, verbose, and fragile across class versions (`serialVersionUID` mismatches cause `InvalidClassException`).
- **Mitigations if you must use it:**
  - **Deserialisation filters** (`ObjectInputFilter`, JEP 290/415) allowlisting classes.
  - Never accept serialised objects from the network.

**Use instead:**

- **JSON** (Jackson):
  - **Never enable default typing / polymorphic deserialisation from untrusted input** (`enableDefaultTyping` is the Jackson gadget vector). Use explicit `@JsonTypeInfo` with a **closed set** of subtypes.
  - Configure `FAIL_ON_UNKNOWN_PROPERTIES` deliberately (false for tolerant readers).
  - Records are supported.
  - Use `JavaTimeModule` for `java.time`.
- **Protobuf / Avro** for compact, schema-evolving binary formats between services (see [API Design](/docs/api-design)).
- **Kotlin:** `kotlinx.serialization` is compile-time and reflection-free.

### How do you benchmark and optimise Java code correctly?

**Naive benchmarks lie** (`System.nanoTime()` around a loop):

- **JIT warm-up:** the first iterations measure the interpreter.
- **Dead-code elimination:** the JIT removes work whose result you never use.
- **Constant folding**, **on-stack replacement** effects, GC noise, CPU frequency scaling.

**Use JMH** (Java Microbenchmark Harness):

**Optimisation priorities, in typical order of impact for backend services:**

1. **I/O and the database:** N+1 queries, missing indexes, chatty remote calls, no connection pooling.
2. **Algorithms and data structures:** O(n²) loops, `List.contains` in loops (use a `HashSet`), linear lookups.
3. **Allocation rate:** boxing in hot loops, needless copies, `String.format` in logging (use parameterised logging: `log.debug("x={}", x)`), giant temporary collections.
4. **Contention:** `synchronized` hot spots, a too-small connection pool, a single-threaded executor bottleneck.
5. **GC tuning and JVM flags last.**

**Collections reality check:**

- `ArrayList` beats `LinkedList` for almost everything, even mid-list inserts at moderate sizes, because of CPU caches.
- **`ArrayDeque`** is better than `Stack` and `LinkedList` for stacks and queues.
- **`EnumMap`/`EnumSet`** for enum keys.
- Primitive collections (fastutil, Eclipse Collections) for huge numeric datasets.
